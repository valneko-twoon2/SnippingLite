# テストケースの設計

仕様から、検証するケースの一覧を、テストを書く前に作る。surveying-tests で始めたテスト群の一部であり、すべてのテストに
共通する規則が適用される（期待値は仕様から取る、1 テストにつき 1 つの振る舞い、拒否したら何も変わらない、
テストが一度は失敗するのを見る）。

1. 対象が何を読み、何を決めるかを、仕様（README、docs、docstring、チケット）から読む。コードからは読まない。
2. 対象について [reference/case-design.md](reference/case-design.md) のケース表を書く。同値分割、単位つきの境界値、
   分岐と条件の対、2 つ以上の入力が絡むときは決定表、ライフサイクルなら状態とイベントの表、悪意ある入力、性質。
   リファレンスに各項目の実例がある。
3. すべてのケースに、仕様または手計算から期待値を付ける。仕様が何も言っていないケースはテストに入れず、
   持ち主への質問に回す。
4. ケースごと、または小さなまとまりごとに 1 つテストを書き、名前は規則にちなんで付ける（`accepts a file of exactly the limit and refuses
   one byte more`）。拒否の後は、ほかに何も変わっていないことを検証する。
5. 表と、テストを付けていないセルとその理由を報告する。カバレッジツールは同値分割、境界値、条件の対を測らないので、
   表が計画であり証拠である。

対象が外部（ファイル、リクエスト、コマンド）から入力を受けるときは、randomizing-tests でシード付きのランダム入力も計画する。
途中で止まりうる複数ステップにわたって状態を持つときは、testing-systems を見る。
