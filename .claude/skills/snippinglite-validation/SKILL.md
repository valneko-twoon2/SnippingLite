# SnippingLite の検証

コミットする前に `pwsh -File scripts/validate.ps1` を実行する。キャプチャや UI を変更した場合は、リリースバイナリをビルドし、キャプチャ、キャンセル、クリップボード出力、ショートカット登録、可能ならマルチモニターを試す。試していない動作は正直に報告する。主要な流れはエンドツーエンドテストが同じことを行う。`cargo test --manifest-path src/Cargo.toml --config src/.cargo/config.toml --test e2e -- --ignored --test-threads=1` は、一時的な設定とフォルダーでアプリを起動し、既知の背景でプライマリモニターを覆って、マウスとキーボードで操作する。アプリはツールバーをポインターのあるモニターに出すので、テストはショートカットを押す前にポインターをプライマリモニターの決まった位置へ置き、テストの終わりに元の位置へ戻す。アプリは、ビルドした exe を一時フォルダーの決まったパス（`%TEMP%\snippinglite-e2e-exe\snippinglite.exe`）へ写して起動する。Windows はトレイのアイコンを exe のパスごとに `HKCU\Control Panel\NotifyIconSettings` へ記録するので、worktree ごとのパスから起動すると、設定の「そのほかのシステム トレイ アイコン」に Snipping Lite が worktree の数だけ増える。写しはテストの後も残り、次の実行が同じパスを使う。実行中は Snipping Lite を閉じ（トレイだけでなく、設定・履歴・プレイヤーの窓も。テストするアプリは撮影のたびにそれらの窓を隠すので、ほかのプロセスに残っていれば、テストは始めずに止まる）、マウスに触れないこと。テストはキーやボタンを押す前に、前面の窓とポインターの下の窓がテストかアプリのものかを確かめ、ほかのアプリには入力を送らない（窓が切り替わる途中で前面の窓がない瞬間は、ほかのアプリの窓とみなさず、待って見直す）。ほかのプロセスの窓（ほかの作業が開いた端末など）が前面に出たり、テストの置いたカーソルが動かされたりした回に失敗したテストは、3 回まで初めからやり直す。やり直しの知らせ（失敗の内容を含む）と、各テストの終わりのやり直した回数（`E2E: <テスト名>: やり直し N 回で通った`）は、libtest が捨てない標準エラーへ直接書くので、成功したテストでも通常の実行の出力に残る。そうした邪魔のないまま失敗したテストはやり直さない。キャプチャ、ツールバー、録画、履歴ウィンドウを変更したときに実行する。完了を報告する前に `pwsh -File scripts/complete-task.ps1` を実行する。

テキストの配置: `scripts/check-text-alignment.ps1` は `validate.ps1` の一部として実行され、上端・下端のテキストアンカー、`DT_VCENTER` のない `canvas.text`、日本語フォントのオフセットの削除を検出して失敗する。UI を変更したときは、設定ウィンドウと履歴ウィンドウもキャプチャし、すべてのラベルがトグル・ボタン・行に対して上下中央にあることを目で確認する。`// align-ok` を足すのではなく、原因（アンカーやフォントのオフセット）を直す。

カバレッジ: `pwsh -File scripts/coverage.ps1` はアプリケーションコードの行カバレッジを測定し（目標かつ既定のしきい値は 95%）、ユニットテストと `#[ignore]` 付きのテストを一緒に実行する。後者はウィンドウを作り、画面を覆い、クリップボードを使い、ダイアログやメニューを表示し、エクスプローラーを開く。そのため、実行中の Snipping Lite を先に停止し（終了後にまた起動すること）、出力が 120 秒止まった実行はやり直し、実行中はマウスとキーボードに触れず、普段使いが必要なマシンでは実行しない。各テストは実際のトレイ状態（`test_support::desk::Desk`）を作り、メッセージループとマウスの役を演じる。egui の画面はウィンドウなしで動かす（`test_support::screen::Screen`）。エンドツーエンドテストとテスト用ヘルパーは測定の対象外。

ファイルの長さ: `scripts/check-file-length.ps1` は `validate.ps1` と Stop フックで実行され、`.rs`、`.ps1`、`.cmd` のファイルが 500 行を超えると失敗する。Claude Code も Edit や Write のたびに実行し、フックが該当ファイルをすぐ知らせる。責務ごとにファイルを分割し（子モジュールのファイル、または `tests/` 配下の話題別テスト）、テストはすべて残すこと。テストやコメントを削って短くしない。分割後は `cargo test --no-run` を実行する。移した項目に `pub(super)` や `pub(crate)`、親モジュールの `use child::*;` が必要になることがあるため。

その他のチェック: `validate.ps1` は `scripts/test-installer.ps1` を実行する。これは `install.ps1` と `uninstall.ps1` をローカルの Web サーバーに対して試す（チェックサム不一致、再インストール、ユーザーが追加したファイル）。リリース前にはリリースビルドに対して `pwsh -File scripts/smoke.ps1` を実行する（リリースワークフローも実行する）。一時的な設定で exe を起動し、メインウィンドウを待ち、トレイのコマンドで終了させる。事前に Snipping Lite を閉じること。`scripts/check-workflows.ps1` はバージョンを固定した actionlint で GitHub のワークフローを検査する。`src/leaks.rs` のリークテストはプロセス全体の GDI と USER オブジェクトを数えるため、既定では無視され、`coverage.ps1` が単独で実行する。手で実行するには `cargo test ... leaks -- --include-ignored --test-threads=1` を使う。公開済みの全レイアウトの設定ファイルは `src/config/tests/compat.rs` にフィクスチャとして置いてある。設定を追加するたびに、そこへレイアウトを足すこと。

インストーラー: `install.ps1` と `uninstall.ps1` は mixerplus のインストーラー（E:\Code\mixerplus）に倣っている。ユーザー単位のインストール、設定 > アプリ の項目、サインイン時の起動、`snippinglite.exe --version` から読むバージョン、`-Repo` と `-Directory`。`-BaseUrl`、`-RegistryRoot`、`-NoStart` は `test-installer.ps1` のためにあり、レジストリ項目は使い捨てのキーに置く。`publish.ps1` は `artifacts/` にリリース用アセット（exe、そのチェックサム、2 つのスクリプト）だけを残す。ライセンスとサードパーティの通知は exe に埋め込まれ、トレイメニューのバージョン情報ページに表示されるため、依存関係を変えたら `update-notices.ps1` を実行すること。既定の `-Repo` は、リポジトリの名前が SnippingLite であることを前提にしている。
