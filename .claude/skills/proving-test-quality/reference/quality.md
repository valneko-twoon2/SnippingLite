## ミューテーションテスト

ミューテーションツールは、一度に1か所だけ変えてテストを実行する（演算子の反転、定数を1動かす、条件の否定、関数本体を
既定値に置き換える、など）。テストが気づいた変異は**検出**、気づかなかった変異は**見逃された変異**（生き残った変異）
であり、どのテストも確かめていない振る舞いの変化を指す。

1. ファイルを1つ選ぶ。新しいテストが対象にするファイル、または計画の中で最も危険なファイル。先に所要時間（変異の数 ×
   そのファイルを覆うテストの所要時間）を見積もって伝える。長いときはバックグラウンドで走らせる。
2. その言語の標準ツール（tools.md）を実行する。無いとき、または手早く見たいときは下の `scripts/mutate.mjs` を使う。
3. 結果ごとに次のとおり扱う。

| 結果 | 対応 |
|---|---|
| 見逃された。振る舞いがテストされていない（限界、分岐、エラー経路） | この変異で失敗し、本物のコードでは通るテストを足す。規則にちなんだ名前を付ける |
| 見逃された。どんな入力でも変異とコードを区別できない（同値変異） | そのままにする。報告に理由を添えて名前を挙げる |
| 見逃された。実際のネットワーク、デバイス、外部サービスでしか区別できない | 実行で確認した後に限り、ツールの設定で除外し、理由をそこに書く |
| 見逃された。既知の不具合の修正にあたる（その不具合の印付きテストがこの変異でも通る） | そのままにする。不具合とともに名前を挙げる |
| タイムアウト | 中身を見る。ループが進まなくなる変異（動かなくなった添字）は、時間切れで検出されている。上限なしに何かを待つコードやテストには、上限（固定の最大値、締め切り）を付ける |
| ビルド不能 | 何もしない |

4. 同じファイルをもう一度実行する。見逃された変異の一覧には、名前を挙げた同値変異だけが残る。検出・見逃された変異・
   タイムアウト・ビルド不能の数をファイルごとに報告する。1ファイルの点数は、他のファイルについて何も語らない。

テストが多いときは、どの変異や故障がどのテストを失敗させるかの表を作る（実行ごとのテスト別出力から）。どの変異でも
失敗しないテストは、空洞か、他のテストの繰り返しである。

点数はファイルごと、ツールごとのもの。前後の比較は同じファイルを同じツールで行い、ツールをまたいで比べない。

満点でも正しいプログラムとは限らない。ミューテーションツールが変えるのは演算子と定数であり、コードがどの値を使うかでは
ない。仕様が値引き後の金額で決めると言う規則を小計で決めていても、すべての変異をすり抜ける。仕様から取った期待値が
これを捕まえ、オラクルも捕まえる。オラクルとは、仕様だけから書いた小さな基準実装で、多数の生成入力でコードと突き合わせる
ものである（ロジックを写しただけならスイートには入れない。ケースを見つけるのに使い、見つけたケースを固定する）。

## 同梱のミューテーションサンプラー

`scripts/mutate.mjs` は、テキストだけを見るのでどの言語にも使える。ソースファイル1つとテストコマンド1つを取る。

```bash
node <skill folder>/scripts/mutate.mjs --file src/limits.ts --test "npm test" --lines 1-80
node <skill folder>/scripts/mutate.mjs --file app/rules.py --test "python -m pytest -q tests/test_rules.py" --check "python -m py_compile app/rules.py"
node <skill folder>/scripts/mutate.mjs --file src/parse.rs --test "cargo test --offline parse" --check "cargo check --offline" --max 40
node <skill folder>/scripts/mutate.mjs --list --file src/limits.ts        # what it would change, without running anything
```

- 変えるもの: 比較、等価、真偽、算術、複合代入の各演算子、`!` / `not`、`true` / `false`、数値（末尾の桁を上下に:
  10 → 11 と 9、0.15 → 0.16 と 0.14）、数字だけを持つ文字列（`Decimal("0.15")`）、`if` / `while` の条件全体（否定。
  Python、C 系言語、Rust、Go、Swift）。コメントとその他の文字列の中は対象外。
- 変えられないもの: 名前（`ROUND_HALF_UP`、列挙型のメンバー）、文字列・リスト・表で持つ規則（状態名）、規則がどの変数を
  読むか。規則がこれらに依存するときは、故障を手で書く（故障注入）。
- テストコマンドは、そのファイルを覆うテストだけを実行するものにする。変異ごとに1回走る。
- コミットされていない変更があるファイルは拒否する（先にコミットする。上書きするには `--allow-dirty`）。元のファイルは
  一時フォルダー（Node の `os.tmpdir()`。セッションが書けるのが特定のフォルダーだけなら、TMPDIR か TEMP を、リポジトリが
  無視するフォルダーに向ける）に保管し、変異ごとと終了時に元へ戻し、最後に元とバイト単位で同じであることを確かめる。
  強制終了の後は、`--restore` で元に戻すまで開始を拒否する。
- `.py` ファイルでは、書き込みのたびにそのファイルの `__pycache__` のバイトコードを削除し、コマンドを
  `PYTHONDONTWRITEBYTECODE=1` で実行する。CPython はサイズと秒単位の更新時刻が同じならバイトコードを再利用するので、
  同じ秒のうちに書いた同じサイズの変異が、前の版を実行してしまうおそれがある。
- 実行中は、ディスク上のファイルがほとんどの間変異になっている。終わるまで、フォルダーのコピー、コミット、パッケージ化、
  デプロイをせず、同じファイルに別のツールも使わない。
- `--check` が無いと、構文を壊した変異は検出として数えられる。それを仕分けるために、コンパイルか型の検査を渡す。
- 構文は理解しない。正規表現や書式文字列の中の変異は本物だが、特殊な文字列構文の中の変異は無意味なことがある（同値変異と
  判断する）。
- 同値変異は、冗長なコードの印であることが多い（何も決めない検査、表示されない値）。同じ読みやすさで済むなら行を単純に
  する。そうでなければ、理由を添えて変異に名前を付ける。
- 何かが見逃されたときは終了コード 1 になるので、関門として使える。

## 故障注入

ミューテーションツールは、あらゆる種類のテスト（ファジングのループ、モンキーテストの実行、差分テストの仕組み、クラッシュ
時の整合性のテスト）にも、名前・文字列・表で持つ規則にも届かない。新しいテストの仕組み（ハーネス）ごと、またそうした規則に
ついて、テストが失敗しうることを証明する。

1. テストが確実に通る経路に故障を入れる。ハンドラーでの `throw`、間違った値の返却、飛ばした書き込み、何もしない段階。
   名前・文字列・表で持つ規則なら、別の丸めモード、許可リストに足した状態、正しい変数の隣の変数。
2. 故障が確実に発火することを確かめる。実行が通らない経路の故障は何も証明しない（再描画されたときだけ投げるコンポーネントは、
   何も再描画しなければ到達されない）。
3. 仕組みを実行する。失敗し、どこで失敗したかを示すこと（シードと操作、段階、入力）。
4. コードを戻し、仕組みがまた通ることを確かめる。作業用のコピーで行うか、バージョン管理で戻す。故障はコミットしない。

新しい関門（カバレッジのしきい値、lint 規則、検査スクリプト）も同じ方法で証明する。一度わざと失敗させ（一部のスイートに
しきい値をかける、規則を破る）、実行が止まるのを見る。

## 空洞なテスト: 見るべき兆候

どれも、コードが間違っていても通る。見つけたら直し、報告に件数を書く。

| 兆候 | 空洞な理由 | 代わりに |
|---|---|---|
| 「null でない」「真」「型」「緩い範囲」だけを検証する | ほとんどどんな誤った値でも通る | 仕様どおりの正確な値 |
| `assertRaises(Exception)`、型を指定しない `toThrow()` | タイプミス（`TypeError`、`NameError`）が、期待した拒否として通ってしまう | エラーの型とメッセージの一部 |
| 期待値をテスト対象のコードで計算する、またはその出力から写す | 今日の不具合が期待値になる | 手計算か仕様の例 |
| 出てきた結果ではなく、モックが呼ばれたことを確かめる | 結果が間違っていても通る | 結果を検証する。モックは端だけに使う |
| テストの中の `if` やループ | 検証が一度も走らないことがある | 一直線のテスト。ループの回数を検証する |
| 空かもしれないケース群へのループ | ケースが0なら検証も0 | 実行したケースの数を検証する |
| 全体のスナップショットを、読まずに更新する | コードの動作が何であれ記録する | 選んだ出力のスナップショット、差分は読む |
| 待つための sleep | 遅く、負荷で不安定になる | 締め切り付きで条件を待つ |
| テストの中でエラーを捕まえて無視する | 失敗を隠す | 失敗させる |
| 関数本体が既定値に置き換わっても通るテスト | 結果を何も確かめていない | ミューテーションの実行で分かる |

## 不安定なテスト

- 新しいテストは何度も（ループで10回）実行し、さらにマシンが忙しいとき（スイート全体を並列で）に1回実行する。負荷のもとで
  だけ失敗するテストは、条件ではなく時間を待っているか、状態を共有している。
- 探す原因: 実時間と日付、テスト間の順序、共有ファイルやグローバル、実際のネットワーク、待っていない promise やスレッド、
  使用中のポート、シードのない乱数、片付けていない資源。
- 重い実行（ブラウザーのスイート、ミューテーションの実行）が別の実行とマシンを分け合うと、遅いテストがタイムアウトする。
  不安定と呼ぶ前に、空いたマシンで再実行し、重い実行が重ならないようにする。
- ランナー設定の再試行は不安定さを隠す。足さずに、報告する（棚卸しに載っている）。

## してはいけないこと

- スイートを通すために、失敗するテストを弱める、飛ばす、消す、または期待値をコードの出力に変える。
- 関門を通すために、カバレッジのしきい値を下げる、またはファイルをカバレッジから外す。
- 変異や注入した故障をコミットする、またはテストの仕組みが出した作業用の出力をリポジトリに残す。
- 行カバレッジだけでテストスイートを良いと言う、または1ファイルのミューテーションの点数をもとに、モジュール全体を
  カバーしたと言う。
