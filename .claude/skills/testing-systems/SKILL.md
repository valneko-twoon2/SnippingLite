# システムテスト

コードの境界（ストレージ、プロセス、ネットワーク、UI、バージョン、ビルド）をまたぐテスト。surveying-tests で始めたテスト群の一部で、同スキルが定めるすべてのテスト共通の規則（一時フォルダーを使う、利用者の実データや動作中のプログラムに触れない、時間でなく条件を待つ）に従う。

1. プロジェクトがまたぐ**境界を洗い出し**、きっかけの条件が当てはまる種類を選ぶ（surveying-tests の種類の表に、各種類と最初のテストが載っている）。
2. [reference/systems.md](reference/systems.md) の説明に従って、**各種類の最初のテストを書く**。

| 種類 | 最初のテスト |
|---|---|
| 結合テスト | 実際の一時データベースまたはフォルダーを 1 つ、偽サーバーを 1 つ |
| 契約テスト | 通信で使う型ごとにサンプルファイルを 1 つ置き、両側で検査する |
| スナップショット | 変種ごとに 1 つ。更新は、新しい出力が意図したものだという表明 |
| E2E | 実際の入口を通る主要な操作の流れ |
| 複数ブラウザー、見た目、アクセシビリティ | E2E の一部を WebKit と Firefox で実行する。スクリーンショットの基準画像。画面ごとの axe 検査 |
| クラッシュ時の整合性 | 手順 k のたびに停止して再起動し、完全な 1 つの版であることと、残骸がないことを確かめる |
| 旧データ | 旧リリースが書いた入力データ。再生成しない |
| リリース確認（スモーク） | ビルドした成果物を起動し、実際のリクエストを 1 回送る |
| 性能、監査 | 上限値つきのベンチマーク。そのエコシステムの監査コマンド |

3. **クラッシュ時の整合性には継ぎ目が要る**。手順 k の後で止められるステップ関数かフックのこと。コードにそれがなければ、その旨を報告し、リファクタリングの前に確認を取る。それまでの間は、ファイルシステムの端で故障を注入し（ロックされたファイル、書き込み拒否）、並行する読み手をテストする。後者は確率的なので、その旨を明記する。
4. 言語ごとのツール（Playwright、insta、監査コマンド）は [reference/tools.md](reference/tools.md) にある。
5. 各テストの仕組み（ハーネス）が失敗できることを示す。到達する経路に故障を入れ、検出されるのを確かめる（proving-test-quality）。

システムテストの標的に、利用者が動かしているアプリケーション、実データのフォルダー、アカウント、認証情報を決して選ばない。一時フォルダー内の複製を使う。
