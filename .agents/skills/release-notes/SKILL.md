# SnippingLite のリリースノート

テンプレートをコミットから埋める。コミットにない変更は書かない。

## 手順

1. `docs/release-notes-template.md` を先頭のコメントまで全部読む。書き方の規則（日本語、1 行の箇条書き、画面の言葉、節の構成）はそこにある。
2. 範囲を決める。前のタグは `git describe --tags --abbrev=0` で調べる。タグがまだ無いときは最初のコミットから `HEAD` までを範囲にする。利用者がバージョンや範囲を指定したら、それに従う。そのうえで `git log --no-merges --format="%h %s" <タグ>..HEAD` を読む。
3. コミットを分ける。`feat:` は「新機能」、`fix:` は「修正」、分かっている制約は「既知の制限」に入れる。利用者に見えないもの（`docs:`、`chore:`、`test:`、`build:`、`ci:`、ハーネス、リファクタリング）は書かない。関連するコミットは 1 項目にまとめる。ある機能を足した後で直したコミットは、足した機能の 1 項目にまとめる。
4. 件名だけでは利用者に何が変わったか分からないときは、差分を読む（`git show --stat <id>`、続けて必要な部分）。ボタンや設定の名前は、`src/` の画面の文字列を検索して、画面に出ている言葉をそのまま引く。数値（日数、件数、既定値）は推測せず、コードから取る。
5. テンプレートの構成と口調で書く。1 行の箇条書きだけにし、小見出しや段落は足さない。空の節は消す。「インストール」の節はそのまま残す。
6. Markdown を ```` ```` ```` のコードブロックに入れて出力し、そのまま本文に貼れるようにする。使った範囲（`v0.1.0..HEAD`、N コミット）と、利用者に見えないとして外したコミットも伝える。

## 守ること

- `gh release create`、`gh release edit`、push、タグ付けは実行しない。公開は利用者の作業で、頼まれたときだけ行う。
- 頼まれない限り、ノートをリポジトリに保存しない。
- 内容がはっきりしない変更や、確かめられなかった変更は、事実として書かず、質問として別に挙げる。
- `.github/workflows/release.yml` は `--generate-notes` で本文を自動生成する。このスキルの本文を使うなら、利用者がリリース作成後に本文を置き換えるか、`--notes-file` に変える。
