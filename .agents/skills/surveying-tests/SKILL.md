# テストの棚卸し

6 つのテストスキルの入口。プロジェクトに何が必要かを調べ、計画を立て、各部分を担当するスキルを示す。すべてのテストが守る規則もここにある。6 つのフォルダーはまとめて導入する。

| スキル | 内容 | 使いどころ |
|---|---|---|
| surveying-tests（このスキル） | 棚卸し、種類の表、計画、報告 | 作業の最初と最後 |
| measuring-coverage | 行と分岐のカバレッジ、どのテストも読み込まないファイル | 「コードを実行しているか」 |
| designing-test-cases | 同値分割、境界値、条件、決定表、状態、悪意ある入力 | 何を検証するかの選定 |
| randomizing-tests | 性質ベース、モデルベース、ファジング、差分テスト、モンキーテスト | 誰も書き出していない入力 |
| testing-systems | 結合、契約テスト、E2E、クラッシュ、旧データ、リリース、その他 | プロジェクト全体 |
| proving-test-quality | ミューテーションテスト、故障注入、空洞なテスト、不安定なテスト | 「不具合に気づけるか」 |

テストが十分と言えるのは、次の 3 つの問いそれぞれに実測の答えがあるとき。コードを実行しているか。このプロジェクトで起こりうる失敗を探しているか。コードが間違っていたら気づけるか。カバレッジが高くても答えられるのは最初の問いだけである。結果を確かめずに行を実行するテストでも、その行はカバーしたことになる。

スクリプトは Node 18 以上が必要。このスキルのフォルダーのパス（以下の `<skill>`）で実行する。どのスクリプトも `--help` で使い方を表示する。

```
テストの作業:
- [ ] 1. 棚卸し: 技術構成、テストの実行方法、既存のテスト、種類の表、仕様
- [ ] 2. 基準測定: スイートの結果、カバレッジ（行、分岐、読み込まれていないファイル）、質の標本
- [ ] 3. 計画: 最も危険な穴から、それぞれ担当スキルに振り分ける
- [ ] 4. 仕様からテストを書き、それぞれ一度は失敗するのを見る
- [ ] 5. 見つかった不具合: 失敗するテストを残し、修正か既知の不具合の印、同じ不具合を他でも探す
- [ ] 6. 質の証明: 変異や注入した故障が検出される、見逃された変異を処理する
- [ ] 7. 測り直して報告: 前と後、実行したものと実行しなかったもの
```

## 1. 棚卸し

1. `node <skill>/scripts/inventory.mjs <repository>` を実行する。言語、テストの実行方法（マニフェストのスクリプト、CI、README に書かれたテストコマンド）、テストファイル、種類ごとの手がかり、同名のテストが無い大きなソースファイルが表示される。読むのは名前とマニフェストだけなので、報告された種類ごとにファイルをいくつか開き、スクリプトに見えない種類も探す。
2. [reference/matrix.md](reference/matrix.md) の種類の表を埋める。各種類を「ある」「一部」「無い」で示し、根拠のファイルと、その種類が必要になる条件がこのプロジェクトに当てはまるかを書く。
3. 仕様を読む。README、docs、API ドキュメント、docstring、課題、変更履歴、不具合の履歴（`git log --oneline -i --grep=fix -- <path>`）が対象。テストは仕様が言うことを検証する。仕様が何も言っていない箇所は前提を書き留め、答えによってテストが変わるなら持ち主に尋ねる。
4. プロジェクトがテストを実行する方法を調べ、同じコマンドを使う。

## 2. 基準測定

1. スイート全体を一度実行する。成功、失敗、スキップの件数と所要時間を記録する。すでに失敗する、または結果が揺れるテストは、見つけたものとして報告する。黙って直したり、スキップしたり、削除したりしない。
2. 分岐を含め、すべてのソースファイルを対象にしたカバレッジを測る。measuring-coverage スキルを使う。
3. 何かを変える前に、最も重要なモジュールの質の標本を取る。proving-test-quality スキルを使う。行カバレッジが高いのに見逃された変異が多いなら、「テストは通るが不具合は出荷される」型である。テストがまだ無い場合は、代わりに変異の数（`mutate.mjs --list`）を記録する。
4. 基準の数値を書き留める。報告はこれと比べる。

## 3. リスクによる計画

候補（モジュール、関数、足りない種類）に順位をつけ、依頼に収まる上位を取る。1 回の作業では通常 3〜5 件。

- **影響**: 金銭、データ消失、安全の境界（パス、認証、利用者・ファイル・ネットワークから読むものすべて）、保存データとアップグレード、公開インターフェース。
- **起こりやすさ**: 分岐と算術、構文解析、上限、状態とライフサイクル、並行処理、最近の変更と不具合修正。
- **露出**: 通っていない分岐、見逃された変異、必要になる条件が当てはまるのに無い種類。

計画は表にする。項目、リスク、種類、担当するスキル（種類の表の最後の列）、ケース。依頼を超える作業（新しいツールやサービス、CI の変更、テストしやすくするためのコードの書き換え）は、先に確認する。

## 4. すべてのテストの規則

セットのどのスキルもこれに従う。テストは計画が指すスキルで書く。

- 期待値は仕様か手計算から得る。コードの現在の出力から取らない。
- 1 つのテストで 1 つの振る舞いを検証し、その振る舞いを名前にする。結果（値、エラーの型、状態、イベント、ファイル）を検証し、拒否のあとは、ほかに何も変わっていないことも検証する。
- 偽物は境界だけに使う（時計、ネットワーク、一時フォルダー内のファイルシステム、シード付きの乱数）。テスト対象そのものはモックにしない。
- シェル経由でテストファイルを書いたら、バックスラッシュや `\0` が制御文字に化けていないか確かめる（コミット前に NUL などの制御バイトを検索する）。
- 決定的にする。固定のシードを使い、長く回すときは環境変数で上書きできるようにする。sleep は使わず、期限つきで条件を待つ。すべてのループは定数で上限を設ける。
- 隔離する。一時フォルダーはテストが失敗しても消し、名前にプロセス ID を入れる。テスト間で状態を共有しない。作業用の出力はリポジトリが無視するフォルダーにだけ置く。利用者の実データ、アカウント、認証情報、動作中のプログラムには触れない。悪意あるパス（`..`、`C:\x`）は、そのテスト自身のフォルダーの中だけに向ける。
- 足りない仕組みは用意する。言語に付属のランナー、プロジェクト標準のテストコマンド、カバレッジのコマンド。依存を足すのは、組み込みの機能では足りないときだけで、足したことを伝える。
- **各テストが一度失敗するのを見る**: 守っている行を壊す（または、倒すはずの変異を当てる）。名前にある理由で失敗するのを確かめ、行を戻す。戻すときに作業を失わないよう、先にコミットする。失敗しえないテストは、直すか削除する。
- 通すために、失敗するテストを弱めたり、スキップしたり、削除したりしない。しきい値を下げない。ファイルを除外しない。
- 作業中は触ったテストを実行し、最後にスイート全体を実行する。

## 5. テストが不具合を見つけたとき

1. まず仕様と照らして、テストとコードのどちらが間違っているかを確かめる。仕様が不明確なら、選ばずに尋ねる。
2. 失敗するテストは残す。それが回帰テストになる。修正が依頼に含まれるならコードを直し、修正後にテストが通るところを示す。修正ごとに、その回帰テストと一緒にコミットする。ほかの新しいテストとは分け、どのコミットも通り、修正を単独で取り消せるようにする。2 つの不具合が絡み、片方の修正だけではテストが通らないときは、1 つのコミットにまとめるか、先に残りへ既知の不具合の印を付けてから直し、そう判断したことを報告に書く。利用者にとって何が変わるかも書く。含まれないなら既知の不具合として印を付け、理由を書いて見えるようにしておく（[reference/known-bugs.md](reference/known-bugs.md): ランナーごとの印と、印が不具合以外のものまで隠す場合）。
3. 同じ不具合がほかにないか探す。同じ演算子やパターン、兄弟の関数、同じ規則のほかの上限。何を探し、いくつ見つけ、いくつ直したかを報告する。
4. 期待値をコードの出力に合わせて変えない。

## 6. 質の証明

proving-test-quality スキルを使う。新しいテストの対象ファイルへの変異、ミューテーションツールが届かないテストの仕組みへの故障注入、10 回連続の実行、負荷をかけた状態での 1 回の実行。

## 7. 報告

- 前後の比較: 種類ごとのテスト数、触ったファイルごとと全体の行・分岐カバレッジ、どのテストも読み込まないファイル、標本にしたファイルのミューテーションの件数（検出、見逃し、タイムアウト、ビルド不能）、変わった行を示した種類の表。
- ケースの表と、テストを書かなかったセルや行とその理由。
- 見つけた不具合: 失敗するテスト、修正または既知の不具合の印、同じ不具合の探索とその件数。
- 持ち主への質問: 仕様が扱っていない入力と、結果が意図しないものに見える規則。
- 実行した各コマンドとその結果。実行しなかったものとその理由（ツールが無い、時間、範囲外）。成功、失敗、未実行を分けて書き、測っていないコードに結果を広げない。
- 残った最大のリスク。次の手順として書く。
