# テストの質を証明する

「コードが間違っていたら、テストは気づくか」に答える。surveying-tests で始めたテスト整備の一部であり、すべてのテストに
共通する規則が適用される。特に、テストを弱めない・飛ばさない・消さないこと、わざと壊す前にコミットすること。
サンプラーには Node 18 以上が要る。このスキルのフォルダーのパスを指定して実行する（以下の `<skill>`）。

```
質の作業:
- [ ] 1. ファイルを 1 つ選び、所要時間を見積もり、それを覆うテストを見つける
- [ ] 2. ミューテーションを実行する（言語の標準ツールかサンプラー）。スコアを記録する
- [ ] 3. 見逃された変異すべて: テストを足すか、理由を書く
- [ ] 4. ミューテーションツールが届かない仕組み: 故障を入れ、失敗するのを見て、コードを戻す
- [ ] 5. 新しいテストを 10 回続けて、負荷のかかった状態で 1 回実行する
```

1. **ファイルを選ぶ**: 新しいテストが対象にするファイル、または計画の中で最も危険なファイル。見積もり（変異の数 ×
   それを覆うテストの所要時間）を出して伝える。長い作業はバックグラウンドで走らせる。
2. **実行する**: その言語の標準ツール（[reference/tools.md](reference/tools.md)）。手早く見たいときは、どの言語でも
   `node <skill>/scripts/mutate.mjs --file <source> --test "<command>" [--check "<compile check>"] [--lines a-b]`。
   先に `--list` で数を数える。サンプラーはコミットされていない変更があるファイルを拒否し、変異ごとにファイルを元に戻す。
   実行中のディスク上のファイルは変異そのものなので、終わるまでそのファイルのコピー、コミット、他の作業をしない。
3. **見逃された変異を1つずつ処理する**: [reference/quality.md](reference/quality.md) の表に従う。その変異で失敗する
   テストを足す、同値変異として理由を添えて名前を挙げる、または既知の不具合の修正として残す。タイムアウトはすべて確認する。
   再実行する。見逃された変異の一覧には、名前を挙げたものだけが残る。既知の不具合に印を付けたテスト（node:test の todo など）
   があると、その修正そのものの変異は必ず生き残る。仮に修正を当てて印付きのテストが通ることを確かめ、不具合の名前を添えて残す。
   `Decimal("0.01")` を `"0.02"` にしても結果が変わらないような、桁だけが違う定数も同値変異になりやすい。
4. **残りには故障を注入する**: テストの仕組み（ハーネス）、名前・文字列・表で持つ規則、演算子の変異では表せない変数の取り違え。
   手順は quality.md にある（テストが通る経路に故障を入れる、確実に発火させる、失敗が場所を示すのを確かめる、コードを戻す）。
   新しい関門（しきい値、lint 規則）も同じ方法で証明する。
5. **空洞なテストと不安定なテスト**: quality.md に、典型的な兆候（緩い検証、コードからそのまま写した期待値、空かもしれない
   ループ、sleep）と不安定になる原因がある。見つけたら直し、報告に件数を書く。
6. **報告する**: ファイルごとに、検出・見逃された変異・タイムアウト・ビルド不能の数を、同じツールで前後に並べる。満点でも
   正しいプログラムとは限らない。仕様から取った期待値と、仕様だけから書いたオラクルが、演算子の変異では見つからないものを見つける。
